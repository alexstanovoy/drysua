# Безопасность локальных экспериментов

Действует с 2026-09-12 после сообщения пользователя о зависании компьютера.
Причина зависания не установлена: системный журнал предыдущей загрузки был
недоступен текущему пользователю. Нельзя объявлять причиной OOM, CUDA, Turbo
или перегрев без соответствующего свидетельства.

## Обязательный порядок запуска

1. **Не более одной тяжёлой задачи одновременно во всём рабочем сеансе.**
   Обучение, компиляции, полные тесты и матчи выполняются последовательно,
   в том числе если поручены разным субагентам. Параллельно допустимы лёгкие
   чтения и подготовка кода, не конкурирующие за вычислительные ресурсы.
   **Узкое исключение от 2026-09-21:** пользователь разрешил короткие фоновые
   проверки трёх concurrency-прототипов рядом с текущим frozen B40, допуская
   небольшое замедление, но не остановку основного обучения. Одновременно
   разрешена только одна такая проверка; не второй полноценный training run.
   Фоновый процесс запускается с nice 19 в отдельном собственном cgroup:
   high 10 GiB, max 12 GiB, swap 0, pids 512, без CPU quota/affinity. CPU-проверки
   ограничены 240 секундами, отдельный GPU-прогон — 30 секундами, логи — 16 MiB.
   При MemAvailable <24 GiB, свободной VRAM <8 GiB, CPU >85 C, GPU >78 C,
   любом событии ограничения своего cgroup или возрасте текущего training-процесса
   >160 секунд прекращается **только фоновая проверка**. Не трогать основные locks,
   PID/cgroup, checkpoint, frozen binary или команды контроллера. Для взаимного
   исключения фоновых проверок используется отдельный lock. Пока Docker недоступен,
   допустим только уже делегированный собственному пользователю cgroup без команд
   service manager и повышения привилегий; это не считается Docker-миграцией.
   CPU/GPU-нагрузка, состояние основного прогона и причина завершения записываются.
   Замеры рядом с обучением считаются измерениями при конкуренции, не чистым A/B.
2. Внутри Cargo сохраняется обычный параллелизм. Не добавлять `-j1`,
   `--test-threads=1`, affinity, CPU quota или глобальные ограничения библиотечных
   потоков. BIOS, SMT, CCD, частоты и governor не менять самостоятельно.
3. **Новый backend запусков — Docker (решение пользователя 2026-09-21).**
   Не использовать команды host service manager, не менять daemon/socket/groups
   и не переносить работающие процессы. Уже работающие обучение, контроллеры и
   мониторинг не останавливать, не сигналить и не замораживать ради перехода.
   Каждый новый тяжёлый payload должен иметь проверенные фактические ограничения
   собственного cgroup v2. Для Docker принят более строгий профиль:

   ```text
   memory.max=12884901888       # Hard 12 GiB, не прежний Max 16 GiB.
   memory.swap.max=0
   pids.max=1024
   cpu.max=max PERIOD          # Без CPU quota.
   HeavyInvocationMaxSec<=300  # Включая резерв завершения.
   ContainerStopGraceSec=5
   Restart=no
   ```

   `mem_reservation` **не устанавливает `memory.high` на cgroup v2**. Нельзя
   объявлять его эквивалентом прежних High=12G / Max=16G. Hard 12 GiB выбран
   как более строгая граница без привилегированной записи в cgroup; при отказе
   нельзя автоматически повышать его до 16 GiB. Проверять реальные файлы
   собственного cgroup до CUDA, а не только декларацию Compose.

4. До старта требовать `MemAvailable >= 24 GiB` и минимум `4 GiB` свободной VRAM.
   Во время работы, не чаще одного раза в секунду, контролировать память,
   температуру и cgroup events. При `MemAvailable < 16 GiB`, VRAM ниже `4 GiB`,
   CPU выше `90 C`, GPU выше `85 C` или событии memory/pids limit — останавливать
   только собственную задачу. Отсутствие доступного температурного датчика
   записывать как отсутствие измерения, не как нулевую температуру.
5. Логи ограничивать: `1 GiB` payload на сессию, `16 MiB` телеметрии ресурсов
   на сессию, `16 MiB` json-file лога Docker. Перед сессией требовать `16 GiB`
   свободного диска, во время работы останавливаться ниже `4 GiB`; более строгий
   `1 MiB` у клиентов оценщика сохраняется. Ограничивать также время ожидания,
   чтение логов и число итераций.
6. Превышение лимита — **не основание автоматически поднять лимит и повторить**.
   Сохранить причину остановки и пересмотреть размер задачи. Перед следующим
   запуском убедиться, что собственные процессы и сервисы завершились.

Исторические watchdog/runner в `artifacts/` остаются свидетельствами старого
backend, а не импортируемыми зависимостями нового. Кампании запускает
`scripts/train.py` (см. [training_controller.md](training_controller.md)):
**один долгоживущий контейнер и один процесс trainer на сессию** (решение
владельца 2026-09-30), а не контейнер на update. Контроллер держит
`owner.lock` кампании и настроенные `lock_paths` (по умолчанию корневой
`heavy.lock`) эксклюзивно и неблокирующе всю сессию; занятость означает отказ.
Если сам контроллер погиб, контейнер может продолжать работу без этих locks до
`recover`, который сначала останавливает записанный контейнер.

Граница остановки — native graceful return: SIGTERM завершает и фиксирует
текущий update, checkpoint пишется после каждого update, поэтому `stop`/kill
теряет не больше одного незафиксированного update. Ошибка ресурса/процесса/схемы
завершает сессию без повторов. Новая сборка обязана честно записывать новый
source/binary hash; strict resume нельзя «чинить» relabel или переключением на
initial weights.

Не переносить в логи произвольное окружение с потенциальными секретами. При смене
каталога журнала не перезаписывать старые spec/result-файлы и свидетельства. Обычный
Docker build **не** получает защиту runtime guard автоматически: пока containment
BuildKit workers не проверен в отдельном согласованном окне, сборки запрещены.
Доступ к Docker daemon пока заблокирован; подготовка конфигурации не означает,
что фактический перенос уже выполнен.

## Checkpoint и восстановление

- **Не использовать SIGSTOP/SIGCONT для архивирования работающего CUDA-процесса.**
  Это исключено как ненужный риск, а не объявлено доказанной причиной зависания.
- Архивировать после завершения процесса либо читать неизменяемую tensor generation
  через согласованный manifest с проверкой SHA. Не смешивать runtime metadata
  с форматом checkpoint: у `checkpoint.safetensors` metadata хранится отдельно.
- После сбоя сначала проверять committed checkpoint, а не только последний лог.
  Возможен сохранённый update, для которого строка журнала не пережила перезапуск.
- До resume сохранять исходные файлы и повреждённые логи без изменения. Читаемый
  префикс повреждённого журнала — отдельный производный файл, не замена оригиналу.
- Не объединять времена до и после перезапуска в вымышленный непрерывный запуск.

## Корректное сравнение производительности

Сравнивать отдельно сбор опыта, оптимизацию, checkpoint, компиляцию и выполнение
тестов. Для обучения закреплять бинарник, начальные веса, seeds, число тиков,
samples и optimizer steps; проверять совпадение наблюдаемых траекторий.
Для тестов закреплять features и состав набора. `cargo test --release` с
722 тестами нельзя сравнивать с all-features набором из более тысячи тестов
как доказательство ускорения процессора.

Разделять Cargo build phase, test body и wall time команды. Тёплый no-op build
не является измерением компиляции; пересборка одного пакета с готовыми
зависимостями не является полной холодной сборкой. Не очищать общие кэши ради
замера без необходимости и отдельного плана.

После перезапуска наблюдались 8 ядер / 8 потоков, SMT off и один L3 96 MiB
вместо прежних 16 / 32. Это соответствует конфигурации одного X3D CCD, но
не является прямым чтением флага BIOS Turbo. Историческое сравнение до/после
не исключает изменения фоновой нагрузки, кэшей и других параметров прошивки.

Результаты последовательных безопасных замеров:
[X3D report](../artifacts/temp/x3d-turbo-20260912/REPORT.md).
Ограничения памяти уменьшают риск истощения ресурсов, но не гарантируют отсутствие
аппаратных сбоев, нестабильности прошивки или ошибок драйвера GPU.
