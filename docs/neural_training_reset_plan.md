# Map0: план пересмотра нейросетевого обучения

Дата: 2026-09-08. Статус: **предложение для обсуждения, не разрешение на запуск**.
Основание: проверка текущего кода, сохранённых экспериментов и первичной статьи
OpenAI Five. Рабочий код, веса, симулятор и deployment при подготовке не менялись.

Проверяемая версия: drysua `8acbc2cc5e174e891192250b9737481c5373b27c`
с уже существующими незакоммиченными изменениями; bota
`18db0f62d9a2b94e755c43fd29a959db204cc20b`. HEAD сам по себе не идентифицирует
грязное дерево: перед будущим экспериментом нужен отдельный source manifest.

## 1. Решение в одном абзаце

Не переписывать протокол, симулятор и проверенную инфраструктуру. Приостановить
увеличение feed-forward модели и перебор коэффициентов полного PPO. Сначала
локализовать ограничение управления и обучения на воспроизводимых эпизодах.
Предпочтительный дальнейший путь: **короткие продолжения настоящих матчей с тем
же условием победы, затем PPO по непрерывным сегментам без сброса игры между
обновлениями**. До перехода на bootstrap-критик проверить и при необходимости
расширить именно value-модель. Рекуррентную память, новое пространство движения
и attention вводить только после диагностического свидетельства их необходимости.
Смена постановки допускает обучение новой политики с нуля; старые артефакты
остаются контрольными, а не обязательной основой каждого следующего запуска.

### Первое предлагаемое разрешение

Один блок **до четырёх часов**: D0–D2 из раздела 5, без длительного обучения,
без final-cohort и без изменения deployment. На выходе — не очередные веса,
а `diagnosis.md`, таблица ошибок по сторонам и решение, какие **не более двух**
вариантов стоит сравнивать обучением. Если диагностика не завершена за этот
бюджет, сохраняем частичный результат и останавливаемся, а не продлеваем запуск.

## 2. Что сохраняется обязательным

- Map0, 1v1, Shadow Fiend. Цель — не менее 80% побед **против каждого согласованного
  предшественника отдельно**, не среднее по пулу.
- В новом боте нет Teacher overrides, safety shield, скриптов покупок или
  скрытых стратегических подполитик. Teacher заморожен: соперник и, при
  необходимости, источник меток, но не объект дальнейшего улучшения.
- Policy, critic и reward получают только разрешённый seat-visible поток и
  ограниченную историю. Никакого World, скрытого enemy state, seed или числового
  entity ID в tensors. Внутренний World допустим только внутри Arena.
- Разрешённые маски проверяют исполнимость команд, а не «правильность стратегии».
  Любое новое ограничение действий отдельно проверяется на исключение полезных
  wire-команд. Текущие ограничения не объявляются автоматически идеальными.
- F32, Candle в model-модулях, без новых зависимостей без обсуждения.
- Только release-тесты. Обычный Cargo parallelism; без новых глобальных
  ограничений jobs/threads, affinity, PGO или уменьшения точности. Ограничение
  четырёх работников в уже зафиксированном оценщике остаётся его контрактом.
- Эксперименты — в `artifacts/temp/`; релизы — в `artifacts/vX.Y.Z/`.
- Старые артефакты не переписываются под новую metadata. Изменение смысла входов,
  выходов, награды или состояния требует новой схемы. Transfer initialization
  явно отделяется от runtime loading и resume, optimizer начинается заново.
- Никаких изменений правил симулятора ради победы. Ни одного нового тега,
  commit, push или переключения default без отдельного решения.

## 3. Факты, поправки к первоначальным гипотезам и неизвестное

| Проверено | Следствие | Чего это не доказывает |
| --- | --- | --- |
| M12 — DeepSets с token-энкодерами, mean/max pooling и условными pointer-heads, 1 689 076 параметров [S1] | Это не просто MLP над списком всех юнитов; «добавить представление сущностей» уже сделано | Pooling достаточно для сложных отношений между несколькими юнитами |
| F11 уже канонизирует Dire position/delta/facing; есть тесты границ и канонической эквивалентности [S2] | Нельзя объяснять Dire отсутствием зеркалирования без нового свидетельства | Реальные стороны карты или стратегии Teacher симметричны |
| Есть active order, его возраст и target geometry; история 16 решений содержит только presence/age/kind; global history — 7 снимков за 480 ticks [S2] | Вход не является снимком «без памяти»; возможный пробел — содержание прошлых целей/слотов и долгий контекст | Однозначность всех Teacher labels или достаточность истории |
| Актор действует каждые 3 ticks при 30 ticks/s; cap 108900 — 3630 секунд от tick 0 [S3] | Максимум 36300 решений; 480 ticks истории — 16 секунд, не 480 решений | Нужно уменьшать частоту управления |
| PPO complete-episodes фиксирует текущего in-process Teacher, пары сторон, retention 1/8 и ждёт завершения пакета [S3] | Это не фактическая тренировка против лиги, несмотря на наличие league-кода | Исторические противники уже покрыты |
| В PPO value loss обучает только линейную голову 256→1 на detached actor representation [S1, S4] | У critic лишь 257 напрямую обучаемых value-параметров; это существенное ограничение для bootstrap | Detach сам по себе математическая ошибка или причина всех поражений |
| PPO sampling и live Neural greedy — разные режимы [S3, S5] | Их силу и управление нужно сравнить явно | Sampling автоматически сильнее или годится для текущего frozen gate |
| Реальный overfit: 64/64 train, 35/64 near-held; всего 8 примеров на kind, Continue отсутствовал [E1] | Градиентный путь способен запомнить маленький набор; entity/sequence generalization подозрительны | Доказана достаточная ёмкость на всей игре или точность 55% на реальной популяции |
| PPO25 LR1e-4: 66 учебных игр, Dire 0/33; новый epochs1: 48 игр, 12W/35L/1T [E2, E3] | Проблема Dire повторяется; учебных исходов мало относительно числа переходов | PPO исчерпан или эффект epochs1 причинно установлен |
| Последний matched DEV: init 0/4, u4 1/4, u8 2/4, все победы Radiant [E3] | u8 стоит сохранить как контроль | Надёжное улучшение, 80% или победы за Dire |
| Serial→parallel E6: 241.1→140.6 s, одинаковые trajectories/targets [E3] | Ускорение 1.72x действительно измерено | GPU насыщен или скорость обучения выросла в 1.72 раза |
| Есть только неполные человеческие записи, без сертифицированных seat observations; exact MovePos coverage 0/64 на Map0 [E4] | Готового human-BC корпуса нет; нельзя выдумывать точные labels | Движение вообще невозможно нашим action space |

**Поправка к первому устному предложению:** не начинаем с повторного добавления
DeepSets, относительных координат или признака собственной команды. Они уже есть.
Также нынешний синхронный complete-episode сбор не создаёт policy-version staleness
во время ожидания: optimizer в это время не меняет веса. Его недостатки — частота
обновлений, корреляция и цена длинного return, а не автоматически «старые градиенты».

Не установлено: первая причинная ошибка за Dire; покрытие полезных действий;
достаточность памяти; точный вклад разницы live/builtin; качество critic вне train;
достаточный для 80% объём опыта. План не подменяет эти неизвестные диагнозом.

## 4. Что берём из OpenAI Five, а что не переносим

Первичный источник: [Dota 2 with Large Scale Deep Reinforcement Learning][paper].
Прочитан сохранённый PDF, 66 страниц; ссылки ниже — на номера страниц этого PDF.

| Результат статьи | Применение здесь | Ограничение переноса |
| --- | --- | --- |
| Recurrent policy, 4096-unit LSTM, около 159M параметров (§3.1, pp.3–4; App.H, pp.45–48) | Память — осмысленная гипотеза для частичной наблюдаемости | Не основание копировать размер или заменять наш DeepSets «с нуля» |
| CPU rollout, GPU inference и optimizer разделены (§3.2, pp.5–7) | Пакетирование и профиль полного матча важнее процента GPU utilization | Кластер тысяч GPU не является проектом для одной 5090 |
| Короткие сегменты продолжающегося матча, 256 timesteps; TBPTT 16 (pp.7,31–32) | Не сбрасывать игру после каждой порции опыта; не ждать конца каждой игры для любого update | Короткий BPTT, горизонт reward и длина памяти — три разные величины |
| Reuse/staleness ухудшали обучение (§4.4; App.M, pp.54–58) | Измерять реальное число использований, корреляцию и policy lag | Для reuse меняли число rollout workers, а значит и разнообразие игр. Это не чистая абляция «epochs4 против epochs1» нашего PPO |
| Sparse reward обучался, но хуже по sample efficiency (App.G, pp.43–46) | Победа-only — честный контроль, но не единственный возможный учебный режим | Их shaped reward не имеет строгой гарантии policy invariance; численные веса не копируем |
| Более длинный горизонт помогал уже сильному агенту (§4.5, pp.14–15) | Удлинять задачи после появления навыков | Это не доказательство, что начинающий агент должен сразу учиться с gamma=lambda=1 на часовых матчах |
| 80% self-play / 20% past opponents (App.N, p.59) | Нужен пул и защита от забывания | Их пропорции не оптимизированы под нашу цель minimum winrate по фиксированным соперникам |
| Rerun обошёл итоговый Five с меньшими затратами (§4.2, pp.10–12) | После стабилизации постановки разумно сравнить fresh и transfer | Перезапуск не гарантирует улучшения, а данные о compute — не прогноз нашего времени |

Важное несовпадение требований: Five оставлял scripted ability builds, покупки,
inventory swap и courier (App.F.1, pp.42–43). **Мы эти скрипты не заимствуем**:
наша цель строже в отношении чисто нейросетевого управления.

## 5. Диагностика перед новым обучением

Все числа ниже — предлагаемые инженерные пороги и лимиты, не измеренные результаты.
Диагностика не использует final seeds. Новые тесты сначала воспроизводят проблему,
затем допускается исправление. Не требуется заново прогонять все старые эксперименты.

### D0. Контракт от наблюдения до фактически отправленной команды

**Вопрос:** одно ли поведение проверяем в BC, PPO и live Neural?

1. Зафиксировать два контрольных артефакта: M12 initializer `adbecb…` и epochs1 u8
   `501734…`, frozen Teacher manifest и бинарники. Полные hashes — в E3 и его
   `base/training.json`. Не использовать случайный `target/release/drysua` после
   сборки wide snapshot.
2. Сопоставить один и тот же разрешённый seat transcript: Tracker → readiness →
   FeatureFrame → masks/candidate order → выбранное действие → decode → persistence.
   Проверить pregame, respawn, исчезновение цели, channel и отказ команды.
3. Сравнивать не только kind: actual wire request может быть подавлен deduplication.
   Новые human/replay labels привязывать к observation/decision/apply ticks,
   а не к ближайшему snapshot по догадке.
4. Отдельно проверить соответствие training Teacher замороженному оценочному
   Teacher на сохранённых trace-пробах. Название enum не доказывает идентичность
   поведения двух сборок. При несовпадении записать его, не заменять baseline.

**Выход:** `contracts.json`, ссылки на минимальные failing/passing tests.
**Стоп:** любое неподтверждённое расхождение в признаках, масках, ticks или отправке.
Известную разницу CPU/CUDA считать численной отдельно от семантической; не обещать
bitwise parity между разными GEMM. Внутри одинакового backend путь должен совпадать.

### D1. Разобрать Dire и режим выбора, а не только посчитать winrate

Предлагаемая матрица: 2 артефакта × 8 seeds `9870000–9870007` × 2 стороны ×
2 режима = **64 игры**. Эти DEV seeds уже не считаются новыми или закрытыми.
Greedy запускается текущим frozen harness. Sampling — только отдельным,
явно названным диагностическим режимом после его проверки; такого live-флага
сейчас нет. Температура sampling 1, один заранее зафиксированный actor RNG на
seed/side; RNG metadata не входит в tensors. Не подбирать «удачный случайный seed».

Если sampled runner не укладывается в первый блок, выполнить 32 greedy игры,
а вторую половину отметить как незавершённую. Не выдавать два разных harness
без D0 parity за чистое сравнение argmax и sampling.

По каждой игре сохранить:

- исход, ticks, сторону, opponent/build/weights identity;
- action counts **и** sent-order counts; longest Continue run с разбиением
  «живой с активной командой / живой без команды / dead / channel»;
- смены body target, повторные команды, время без движения и без боевого события;
- cast requests и наблюдаемые подтверждения cast/damage; предполагаемые отмены
  windup помечать как прокси, если протокол не даёт прямого подтверждения;
- освоение уровня, нераспределённые skill points, доступные покупки и реально
  купленные предметы, inventory readiness, courier activity;
- появление enemy Ancient в доступном наблюдении, наличие его в entity candidates,
  атаки и наблюдаемый прогресс по строениям;
- потерянные из-за cap96/cap48 кандидаты: тип, расстояние, причина отсечения;
  не использовать скрытые юниты как «пропущенные наблюдения»;
- вероятность фактически выбранной ветви, head entropy и legal alternatives.

Не наказывать Continue само по себе: сохранение удачной атаки — полезное действие.
Не ставить диагноз «ничего не делает» по отсутствию новых wire messages.

Вручную разобрать **первую объяснимую развилку**, а не только последний проигранный
бой: до 4 игр, первая по seed для каждой стороны и типа обнаруженного сбоя.
Полный replay — максимум 4 файла по 1 GiB; decision trace — максимум 16 MiB/game;
весь диагностический каталог — максимум 8 GiB. При превышении лимита fail closed,
а не молча обрезать свидетельство. Текущий challenge полных replay не пишет.

**Выход:** `behavior_by_side.csv`, до 4 разборов с tick/наблюдением/командой и
классификацией: невыразимо / информация потеряна / выбор неверен / исполнение
расходится / стратегия не установлена. Гипотеза «Dire = coordinate bug» допустима
только при конкретном контрпримере, не по одному асимметричному winrate.

### D2. Короткий набор проверок управления

Не строим сразу универсальный curriculum engine. Сначала до **24 fixtures**,
по 12 на сторону, с настоящими правилами и известной выполнимой последовательностью.
Test-only `Arena::configure_for_test` существует; production state-reset API нет.
Синтетический fixture проверяет механику, не является результатом полного матча.

| Семейство | Горизонт | Что проверяем |
| --- | ---: | --- |
| Attack → дождаться результата | 150 ticks | Валидная цель, собственный урон, отсутствие самосрыва команды |
| Позиционирование → raze | 300 ticks | Достижимость положения, правильное направление, подтверждённое попадание |
| Добивание | 300 ticks | Собственный last hit в fixture, где он достижим; соседний случай, где удар рано |
| Локальный проход | 600 ticks | Есть маршрут через допустимые points; не зависаем у препятствия |
| Use/Buy/Learn/Swap | 300 ticks | Видимое изменение ресурса/инвентаря/уровня; отрицательные readiness cases |
| Finish structure / recovery | 1800 ticks | Законченный локальный результат, а не бесконечная смена намерения |

Разделить **существование решения через ActionSpace** и способность сети его
выбрать. В первом тесте harness может подать заранее заданную последовательность
для проверки интерфейса. Она не становится runtime controller или новым Teacher.
Любой требуемый waypoint существует в условии теста; не учим основную сеть угадывать
скрытый task goal, которого нет в её входе.

**Стоп:** обязательный манёвр исполним wire-командами, но не ActionSpace. Тогда
сначала A1 из раздела 8. Если всё выразимо, не расширять action space «на всякий случай».

### D3. Условные offline probes, только по результатам D1–D2

- **Information probe:** сравнить conditioned tensors и masks в состояниях с
  разными требуемыми решениями. Разные Teacher labels ещё не означают разные
  правильные действия: сначала проверить игровой результат альтернатив.
- **Critic probe:** на не более 32768 строках из минимум 32 полностью записанных
  training games сравнить константу по стороне/фазе, линейную value-head,
  MLP 256→256→1 на frozen trunk и отдельный trainable critic. Split — по целым
  матчам, минимум 8 игр validation, с обеими сторонами; не по соседним кадрам.
  Если tensors не сохранены, их нужно получить проверенным replay/сбором,
  а не утверждать, что они восстановимы из агрегатного лога.
- Метрики critic: held-out MSE, explained variance отдельно по стороне/фазе,
  raw advantage mean/std и доля почти нулевых advantages. Если variance target
  почти нулевая, EV помечается неопределённой; не делить на epsilon и не хвалить
  предсказание «Dire всегда проигрывает» за понимание стратегии.
- Лимит каждого probe: 1024 optimizer steps и 10 минут. Улучшение validation MSE
  хотя бы на 20% при неизменных actor outputs разрешает RL-абляцию critic,
  но не считается улучшением силы бота.

## 6. Целевая функция: два явно различных режима

### 6.1 Каноническая цель полной игры

Предлагаю отдельный новый training profile:

```text
reward = 1 только при подтверждённой победе до/на допустимой границе матча;
reward = 0 при поражении, ничьей или достижении игрового cap без победы;
gamma_per_tick = 1;
episode_time_cost = 0.
```

Ожидаемая награда тогда совпадает с вероятностью победы в проверяемой задаче.
Переход с ±1 на 0/1 несущественен в двухисходной задаче, но отношение к
таймаутам/ничьим и time-cost существенно. Это **новая семантика**, а не тихое
«исправление» старого PPO25; нужны новая schema/run scope и fresh optimizer.

Различать причины окончания:

| Причина | Reward/continuation |
| --- | --- |
| Авторитетный MatchOver | Terminal, bootstrap 0, outcome из протокола |
| Игровой cap, определяющий невыполненную задачу | `TaskDeadline`, terminal для learner, 0 reward; в отчёте всё ещё timeout, не выдуманный MatchOver |
| Конец порции опыта в живой игре | Не terminal; bootstrap, та же игра продолжается |
| Wall watchdog, повреждение данных, авария процесса | Не игровое поражение; пометить техническую неполноту, не выдумывать training target |

Проверки границы cap должны точно следовать действующему harness: победу не
засчитывать после лимита и не терять допустимый terminal на границе. Технический
timeout оценщика остаётся non-win по его правилам, но не превращается в ложный
учебный MatchOver. Для конечного горизонта добавить доступное время до task cap
в новый input contract; live limit и training limit обязаны совпадать. Нельзя
использовать wall-clock deadline процесса как признак политики.

### 6.2 Учебные промежуточные награды — не изменение определения успеха

Приоритет — короткий suffix с **той же** terminal win reward (раздел 7), а не
новая сумма золота, убийств и урона. Если этого недостаточно, допускается отдельная
абляция плотной награды по наблюдаемым событиям, с frozen формулой и отдельной
оценкой настоящих побед. Новые веса не подбираются после каждого проигрыша.

Не обещать магии от potential shaping. Для
`r'_t = r_t + gamma^dt * Phi(next) - Phi(now)` при `gamma=1`, полном MC и
`Phi(terminal)=0` добавка к return телескопируется в `-Phi(start)`.
При соответственно сдвинутом точном baseline advantage не меняется. Польза
может быть в приближённом critic/TD и обучении представления, а не в появлении
новой информации о том, какое действие выиграло матч. Clipping/budgeting
shaping-компонент также может нарушить стандартную invariance-гарантию.

Поэтому вариант «оставим MC как есть, добавим potential и ждём прорыва» отклонён.

## 7. Выбранный curriculum: настоящая игра с более близким концом

Это предпочтительнее набора разных скрытых task objectives: сеть всегда учится
побеждать, а не угадывать, какой из тестовых reward сейчас включён.

### C1. Обучение на продолжениях зафиксированных партий

1. Получить до 24 полных **training-only** source games: на каждую сторону
   8 source games train и 4 validation. Источники — замороженный Teacher против
   замороженной сети и реальные neural trajectories. Не предполагать, что
   имеющиеся неполные human replay подходят. Teacher при этом не улучшается.
2. Выбрать по правилам, объявленным до обучения, моменты примерно за
   **900 / 3600 / 14400 ticks** до реального terminal: 30 s / 2 min / 8 min.
   Для новой suffix-задачи поставить максимум `min(2 * horizon, remaining_cap)`.
   Это учебный deadline, не сокращённый релизный матч.
3. Воспроизвести весь prefix настоящими requests в pinned Arena, проверить
   transcript/hash и передать управление сети. Никакой подмены HP, золота,
   позиций, damage или победителя в production training.
4. Восстановить seat tracker, readiness, собственные прошлые команды и память
   из настоящего разрешённого prefix. Передача управления и происхождение
   prefix остаются metadata, не сигналом сети. Prefix не попадает в on-policy
   PPO loss; учатся только действия новой suffix-policy.
5. После передачи не сохранять Teacher override и не очищать реальные активные
   orders тайком. Проверить контроль `Continue после передачи`: если исход
   выигрывается уже отданным приказом или крипами, это слишком лёгкий fixture.
6. Не менять поведение соперника одновременно с передачей управления: его
   реализация и состояние должны соответствовать source replay. Смена
   opponent — отдельная ось следующего эксперимента.

Внутреннее состояние соперника, включая RNG, восстанавливается повторным
исполнением его контроллера на prefix с проверкой выбранных действий. Одних
конечных wire requests недостаточно для восстановления решений, подавленных
deduplication, или внутренних переходов Teacher. Если это нельзя воспроизвести,
такой source game не принимается как точный reset fixture.

Для первичной проверки допустимо повторное проигрывание prefix: **мгновенного
Arena restore сейчас нет**. Стоимость reset включается во wall time. Кэш или
private Arena checkpoint — отдельная работа только если reset занимает >20%
времени; любые необходимые изменения bota сначала согласовать. Нельзя обещать
дешёвые короткие эпизоды, игнорируя часовой prefix.

Начальные ограничения: максимум 96 prefix references, 16 одновременно живых
сред, 8 GiB общего training storage для этой линии, 64 MiB/request-prefix file.
Source games и все производные suffix одного матча целиком принадлежат одному
split. Файлы с полной информацией отделены от policy dataset и недоступны
encoder/critic/reward.

### C2. Условия перехода между горизонтами

- Сначала убедиться, что frozen demonstrator решает validation suffix не менее
  чем в 80% попыток, а Continue-control — не более чем в 20%. Иначе набор не
  проверяет нужный навык или недостаточно воспроизводим; не менять пороги
  задним числом для красивого результата.
- Сеть должна решить не менее 80% validation suffix **на каждой стороне**
  на двух заранее выбранных training seeds. Это инженерный curriculum gate,
  не статистический релизный сертификат. Отчёт группируется по source game.
- После освоения 900 ticks: 75% ближайший ещё не освоенный горизонт, 25%
  предыдущий; после 14400 ticks начать обычные игры с tick 1.
- При полноматчевом fine-tuning оставить 25% suffix-задач для защиты от
  забывания; затем убрать их в последнем контрольном этапе и оценить перенос.
- Не вводить curriculum task ID, Teacher intent, known winner или «правильный
  объект» в tensors. Время до учебного deadline доступно по контракту 6.1.

**Стоп линии:** за две заранее ограниченные попытки нет прогресса на первом
валидном горизонте либо прогресс остаётся только на source games train.
Тогда возвращаемся к D2/D3 и не запускаем полный PPO на ночь.

## 8. Конкретные варианты модели и управления

Имена A1/V1/R1 здесь рабочие, **не номера уже существующих schemas**. M13 в
изолированном wide snapshot уже занят отдельным опытом.

### V1. Критик: сначала отделить ёмкость от actor interference

Предпочтение при плохом D3: независимый value encoder/trunk той же структуры,
что у M12, и голова 256→1. Он получает ровно тот же разрешённый FeatureFrame,
не получает hidden state симулятора и не участвует в выборе runtime actions.
Actor остаётся M12; actor/critic optimizer state и clipping раздельны, чтобы
большой value gradient не уменьшал actor update через общий norm clip.

Дешёвый промежуточный probe — MLP 256→256→1 поверх detached actor trunk.
Он добавляет около 66k value-параметров, но не восстанавливает информацию,
которую actor representation уже потеряло. Shared trainable trunk с value
gradient — альтернативная абляция, не одновременно с independent critic.

Тесты: value-only update не меняет ни один actor logit/parameter; critic учится
на различимых return; rollback восстанавливает обе согласованные optimizer
части; old/new value lineage не перепутывается. Начальные LR: actor 3e-5,
critic 1e-4; clip norms по 0.5. Значения — старт профиля, не утверждение об оптимуме.

### R1. Память только при доказанной неоднозначности

Сначала дешёвый input-only вариант: история последних 16 **исполненных** команд
с body, kind, slot, геометрией и семантикой цели на момент отправки, возрастом и
статусом rejection. Не сохранять pointer index как стабильный ID между кадрами.
Не дублировать уже имеющиеся active-order признаки. Для сравнения — тот же
датасет и одинаковый compute budget, без новой награды.

Если этого недостаточно: текущий trunk `z:256` плюс residual memory:

```text
(h, c) = LSTM256(z, previous_h, previous_c)
actor_context = z + projection256(h)
```

Projection начинается с нуля, LSTM — с независимых ненулевых весов. Поэтому
начальный actor может точно воспроизводить M12; это проверяется, не обещается
по форме слоя. Около 591k дополнительных параметров при одном bias на gate,
то есть около 2.28M вместе с M12, без отдельного critic. Общий плановый лимит
actor+critic — 5M F32 параметров. Attention одновременно не добавлять.

Важная инженерная часть: нельзя shuffle отдельных кадров, переиспользовать
устаревший hidden state после изменения весов или учить последовательность,
сохранив только каждый восьмой вход.

Предлагаемый первый ограниченный контракт памяти: блоки по 128 решений
(12.8 s), reset на границе блока и матча, TBPTT до 32 без пересечения границы
блока, восстановление состояния из префикса до 127 шагов без градиента.
Граница collector может разрезать sequence; такой фрагмент имеет отдельную
valid-length mask и не заимствует loss samples другой policy version.
Для нового policy version состояние
пересчитывается из сохранённых входов текущего блока, максимум 127 шагов.
Это сознательно **ограниченная память**, не LSTM с часовым скрытым контекстом.
В rollout сохраняются все промежуточные входы блока, actual actions, masks,
old logprob и reset markers. На этапе R1 dropout не используется.

Тесты: step/sequence parity, CPU/CUDA tolerance, две разные истории при одинаковом
последнем frame, reset isolation, отсутствие cross-seat state, padding mask,
пересчёт hidden при смене policy, resume с точной bounded history. Если ограниченная
память не помогает на заранее выделенных неоднозначных случаях, не увеличивать
LSTM автоматически.

### A1. Движение — только если D2 показывает ограничение

Первый вариант: сохранить 48-point pointer и добавить отдельную ветвь локального
offset для Move/AttackMove. По каждой оси 9 значений
`{-512,-256,-128,-64,0,64,128,256,512}` относительно выбранного controlled body;
81 комбинация, canonical team frame, разрешённая геометрия и проверенный decode.
Предпочтительны factorized `X → Y|X` с точным joint logprob и legality mask;
тестировать map edge, nonwalkable cells и совпадения точек. Это новая action schema.

Зачем: добавить короткие поправки и не конкурировать за cap48 с деревьями,
телепортами и landmarks. Чего не обещаем: точного покрытия произвольных human
MovePos или автоматического знания пути. Для human-BC нужен отдельный доказанный
контракт координат; ближайший grid point не объявляется исходной командой.

Альтернатива при обнаруженном переполнении cap, а не грубой сетке: сначала
исправить резервирование семейств кандидатов без добавления новой ветви.

### Отложенные варианты

- Single-query attention по token embeddings — если actor ошибается на
  контролируемых relational fixtures после устранения coverage/normalization.
  Полный Transformer с нуля пока не оправдан.
- Другая cadence или learned duration — только при подтверждённом command
  thrashing. Сначала сравнение 3 и 6 ticks с одинаковой начальной политикой;
  число шагов и discount измеряются в реальном elapsed game time. Не вводить
  скриптовые «farm/retreat/finish» options.
- Wide M13 оставить как capacity-control. Он пока не доказал игрового улучшения.

## 9. После коротких задач: непрерывный сегментный PPO

Это не возврат к старому collector, который сбрасывал мир до terminal.

```text
8 живых Arena × 512 последовательных решений
  -> 4096 transitions одной версии policy
  -> bootstrap на конце живого сегмента / 0 на настоящем task terminal
  -> один PPO epoch, minibatch 512, microbatch 64
  -> новые веса
  -> продолжить ТЕ ЖЕ Arena, opponent state, trackers и reward accounting
```

Начальный профиль: cadence 3 ticks, retention 1, actor LR 3e-5, entropy .001,
clip .2, target KL .02, gamma 1, lambda .95 **на решение**. При R1 minibatch
содержит целые TBPTT sequences, а не случайные frames. Переход к 16 Arena —
отдельный performance profile, не условие запуска.

Первый вариант синхронный: actor не собирает следующий сегмент во время update;
policy lag 0, один подготовленный batch, bounded worker queue. Асинхронность и
распределённый training framework сейчас не нужны. Частая публикация policy не
означает новый матч. При terminal начинается новая игра по фиксированному schedule.

Нужно проверить: сумма наград и ticks через несколько сегментов, terminal в
первом/последнем шаге, segment boundary непосредственно перед terminal,
сохранение order/readiness/opponent state, корректный bootstrap, отсутствие
обновления без единого валидного sample, восстановление после прерывания.
Сегмент без terminal допустим: иначе снова будем ждать конца каждой игры.
Но запуск должен реально дойти до завершённых матчей, а не отчитаться только
успешными ранними updates. При лимите 108900 и 512×3 ticks нужен минимум 71
сегмент непрерывной игры, чтобы вообще гарантированно достичь cap.

Lambda .95 на новом шаге и lambda .95 на старом retained интервале — **разные
временные масштабы**. На шаге 0.1 s вес следа падает примерно в e раз за 1.95 s.
GAE trace length — не горизонт стратегии: долгий return идёт через critic.
Переход complete-MC → segmented-GAE меняет сразу bootstrap и частоту обновлений;
это сравнение профилей, не чистое доказательство пользы одной длины сегмента.

Ключевой риск: короткий segment плюс плохой critic может оказаться хуже MC.
Поэтому V1/D3 предшествует этой линии, а complete-MC остаётся контрольным.

## 10. Экспериментальная дисциплина и бюджет

### Не запускать все варианты из документа

| Наблюдение диагностики | Первый сравниваемый вариант | Что не менять вместе с ним |
| --- | --- | --- |
| Wire-манёвр невыразим через action candidates | A1 или исправление quota candidates | Critic, reward, recurrence |
| Идентичный доступный контекст скрывает различие прошлых команд | Command-history, затем условно R1 | Geometry, reward, opponent pool |
| Frozen representation плохо предсказывает return | V1 | Actor architecture, action space |
| Управление работает, но полная игра не даёт обучающего прогресса | C1 suffix curriculum | Правила bota, критерий настоящей победы |
| Короткие задачи освоены, полный MC слишком медленно обновляется | Segmented PPO | Новые противники и capacity одновременно |
| Sampling и greedy резко расходятся | Отдельное решение о режиме runtime или distillation | Нельзя переименовать sampled результат в frozen greedy gate |

На первую обучающую кампанию предлагается максимум **6 часов compute**:
два выбранных варианта × два заранее фиксированных training seeds × до 90 минут.
Это бюджет исследования, **не обещание получить 80% за шесть часов**. Подготовка
кода/данных и оценка считаются отдельно и требуют согласования.

Для полной игры cap каждого run — 96 завершённых учебных episodes или 90 минут,
что наступит раньше; для suffix — 2048 episodes или те же 90 минут. Это разные
эксперименты, их sample counts не складываются как эквивалентные полные матчи.
Нельзя запускать новый episode, если лимит уже исчерпан. Неполные batch/episode
от прерывания не выдаются за committed learning. Сравнивать learning curves
по общему достигнутому числу raw actor decisions и отдельно по wall time.

В каждой паре одинаковы train/opponent schedules, начальные условия, evaluation
seeds, число validation checks; shuffle/actor RNG domains независимы от world seed.
При смене архитектуры не обещать одинаковые stochastic trajectories после update.
Число epochs и reuse учитывать по реально применённым minibatches, не по CLI:
KL rollback может остановить эпоху раньше. Checkpoints для оценки — заранее
выбранные середина и конец бюджета, не каждый удачный учебный матч.

**Выбор ветви:** уменьшился диагностический сбой, нет нарушений контрактов,
положительное направление по обеим training seeds и нет очевидного провала
худшей стороны. Малый DEV служит отсевом, не подтверждением статистической силы.
Для финалиста — третья независимая training seed и более широкая confirmation
cohort; при разнонаправленных результатах записывается «неубедительно».

После стабилизации architecture/data/reward сравнить **fresh initialization и
audited transfer** на одинаковой постановке. До этого fresh-run смешает слишком
много причин. Старые веса не удалять даже при победе fresh варианта.

### Оценка инженерных работ, не обещанный календарь

| Этап | Предварительная трудоёмкость | Условие остановки |
| --- | --- | --- |
| D0–D2, первый разбор | 4 h первый ограниченный блок | Недостаточно свидетельств → отчёт и новое решение |
| Надёжный suffix replay/reset и корпус | 1–2 рабочих дня | Нельзя честно восстановить prefix или reset съедает бюджет |
| Независимый critic и его проверки | 0.5–1 рабочий день | Нет offline/generalization эффекта |
| Persistent segmented collector | 1–2 рабочих дня | Нарушается непрерывность игры/return/identity |
| R1 либо A1, если обоснованы | 1–3 рабочих дня на одну линию | Не улучшает заранее выбранные cases |

Не строить весь список заранее. Документ задаёт развилки, а не обязательный
многонедельный rewrite перед первым полезным результатом.

## 11. Соперники и приёмка

После освоения коротких задач, отдельно от collector-абляции, сравнить fixed
Teacher с небольшим смешанным пулом. Начальный proposed schedule полного run:
50% frozen Teacher, 25% последний принятый neural champion, 25% равномерно по
согласованным более ранним противникам. Если champion ещё нет, его место явно
занимает замороженный M12 control, **не выдаваемый за принятый релиз**.
Максимум 8 активных opponent identities. Полный список обязательных соперников
приёмки не сокращается из-за размера training pool; для большого списка —
фиксированная ротация. Никаких live обновлений противника посередине матча.

Старые версии запускаются своим кодом/артефактами, не эмуляцией через сегодняшний
Teacher. Для in-process обучения старым бинарником endpoint сейчас не объявлен
готовым: нужен отдельный adapter с trace parity либо сначала только TCP evaluation.
Наличие `league.rs` не доказывает такой совместимости.

Три разных проверки:

1. **Диагностика/DEV:** многократно используемые ситуации и seeds; разрешён выбор
   checkpoint, запрещено называть результат held-out qualification.
2. **Confirmation:** новые заранее зарегистрированные paired seeds, минимум
   20 пар на обязательного соперника, одна замороженная версия после выбора.
   Не выбирать лучшего из многих checkpoints на этой же выборке.
3. **Приёмка:** frozen Teacher Map0 `9880000–9880049`, 100 игр, ≥80 побед —
   существующий неизменяемый контракт [S6]. Для остальных прошлых вариаций
   нужен отдельный согласованный Map0 manifest и schedule. Исторические Map1
   20 игр и strict >50% не заменяют пользовательскую Map0-цель.

Порог выборочного winrate и уверенность в истинном winrate — не одно и то же.
Показывать uncertainty и paired различия; при resampling группировать по world
seed вместе с обеими сторонами и кандидатами, не по кадрам или отдельным sides.
Не ужесточать существующий gate молча требованием lower confidence bound ≥80%.
При нескольких соперниках отдельно писать, что индивидуальные интервалы не
являются автоматически общей гарантией для всего набора.

Стратегический sanity check: при идеальных 50/50 победах Radiant для 80/100
всё равно нужно **минимум 30/50 побед Dire**. Нулевой Dire нельзя компенсировать
отбором Radiant seeds. Само по себе 80% на каждой стороне не является старым
релизным контрактом; per-side thresholds curriculum не переносить в него молча.

Перед долгой кампанией требуется назвать конечный список «прошлых вариаций»:
четыре зарегистрированных релиза, замороженный Teacher challenge и какие именно
нейросетевые checkpoints обязательны. «Все когда-либо записанные веса» не равно
«все принятые предшественники». По умолчанию сохраняем все принятые релизы плюс
Teacher challenge; пользователь должен подтвердить scope до приёмки.

## 12. Производительность и наблюдаемость

На имеющемся профиле 13976 retained samples и 111809 raw decisions на E6,
140.6 s после CPU parallelism: около 795 raw decisions/s и 99 retained/s.
Это вычисление по одному измеренному workload, не обещание для другого actor,
пула или late-game состояния. Удаление retention увеличивает число сохраняемых
переходов, но не создаёт восьмикратное число независимых игровых ситуаций.

F11 содержит 15038 F32 значений, 60152 bytes без private provenance/metadata.
8×512 frames — около 235 MiB только этих значений; 16×512 — около 470 MiB.
Учитывать masks, history, materialization, копии и Arena отдельно. Начальные
целевые лимиты нового trainer: CPU RSS ≤16 GiB, CUDA allocation ≤12 GiB,
rollout storage ≤4 GiB, общий каталог run ≤16 GiB. Проверить размеры вычислением
и smoke profile до большого запуска; не маскировать OOM снижением точности.

Метрики по каждому update:

- raw decisions, retained/optimized samples, уникальные episodes и prefix sources;
- completed wins/losses/task deadlines по стороне и opponent;
- actor entropy/clip fraction/KL, applied/rejected updates, actor и critic norms;
- held-out critic error и raw advantages, не только усреднённый training loss;
- collection/encode/inference/update/reset/checkpoint/evaluation time;
- CPU RSS, GPU allocation, queue depth, policy-version lag;
- diagnostic rates из D1, отдельно от настоящего winrate.

Идентификаторы конкретного матча/seed/артефакта — в structured records, не в
высококардинальных metric labels. Сначала переиспользовать существующую telemetry,
не строить Prometheus/Grafana ради одного эксперимента.

Отдельно, после learning signal: persistent CPU workers вместо thread spawn
каждый round, batch value/inference, skip Teacher-only encoder work. Каждое
ускорение — на полном workload с trace parity. Сейчас не переписывать симулятор,
не вводить spatial index и не заполнять GPU бесполезным увеличением сети [E5].

## 13. Когда действительно выбрасываем подход

- **Action interface:** обязательные реальные манёвры систематически невыразимы
  → новая схема управления; старый BC dataset не переносится автоматически.
- **Representation:** контролируемые различия видимого контекста потеряны либо
  memory-probe воспроизводимо выигрывает → новый encoder/memory contract.
- **Training path:** даже проверенная короткая задача не учится в двух seeds,
  при корректных labels, gradients и выразимом решении → минимальный новый
  trainer для этой задачи, а не ещё один слой поверх старого pipeline.
- **Curriculum:** умеет только решать переданные выигрышные позиции, но две
  ограниченные попытки не переносятся на начало матча → не наращивать suffix
  corpus бесконечно; пересмотреть распределение и exploration.
- **Transfer:** на стабильной задаче fresh consistently лучше на confirmation
  → прекратить цепочку migrations как основную линию и переобучить политику.

Архивируем неуспех с командой, hashes, seed schedule, метриками и объяснением,
что гипотеза опровергнута или осталась неопределённой. Протокол, честный оценщик,
приватность наблюдений и тесты корректности от этого не выбрасываются.

## 14. Артефакты следующего разрешённого этапа

Предлагаемая структура, **пока не создана**:

```text
artifacts/temp/neural-reset-<run-id>/
  plan.json                 # Frozen hypotheses, caps, seeds, checkpoints.
  source.json               # Dirty source identities + build provenance.
  contracts.json            # D0 parity and known differences.
  behavior_by_side.csv      # D1 outcomes and observable decisions.
  diagnosis.md              # Evidence -> chosen branch, at most two variants.
  fixtures.json             # D2 inputs, source identity, expected properties.
  data_manifest.json        # Whole-match splits and prefix provenance.
  runs/<variant>/<seed>/    # Config, logs, weights, optimizers, counters.
  evaluations/              # Frozen matrices, all outcomes including errors.
  decision.md               # Continue / reject / inconclusive; no auto promotion.
```

Команды нового suffix/segmented/RNN trainer намеренно не приведены: API ещё нет.
Существующий greedy DEV запускается по [инструкции challenge][challenge].
Для будущих изменений Rust обязательны проверки:

```sh
cargo clippy --all-targets --all-features -- -D warnings -D clippy::all
cargo test --release --all-targets --all-features --quiet
cargo fmt
cargo machete
```

При подготовке **этого документа** сборка, тесты, матчи и обучение не запускались.
Проверены источники, ссылки и арифметика плана; это не экспериментальная валидация
предложенных методов. Выполнение любого этапа ждёт разрешения пользователя.
